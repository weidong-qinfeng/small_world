## 3.2 主agent 复核发现的第 9 项（A9）：**后台 QoS 饥饿**——长作业"看起来在跑却慢 10×**

- **现象**：4 个托管 T=120 s 作业（N=250、2.42M 步/臂）运行 **51 分钟**，`ps` 的近期 `%CPU` 显示 **98–100%**，但**累计 CPU 时间仅 4:35**；单个臂实测 `ms/step = 0.088`（同机空白对照 **0.068–0.077**）⇒ **纯计算只需 ~213 s/臂，实际墙钟 2102 s** ⇒ **占空比 ≈10%**。
- **判因**：`ps` 的 `%CPU` 在 macOS 上是**近期采样**，**不是**寿命期占用；**判断进度必须看"累计 CPU / 墙钟"之比**（我此前凭"elapsed=34:39，cputime=3:39"识破，避免了把"调度饥饿"误判成"引擎慢"或"死锁"）。
- **强化既有纪律（L46）**：① 长作业**必须**把"累计 CPU 时间 vs 墙钟"写入进度日志（否则无法区分饥饿与真慢）；② 后台/脱离会话启动的进程可能落入低 QoS 类而只吃余量 CPU ⇒ **长作业要么由主agent 托管并轮询"CPU/墙钟"比，要么降并发**（并发数 ≤ 核数的一半可显著改善）；③ **终止前必须看进度**（L33/L35 的再现：本次若贸然 kill 会白扔 4 个作业）。

## 4.3 主agent 追加发现（A12）：**门 1（自持比）随协议时长系统性漂移**
